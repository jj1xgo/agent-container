# エージェント連携・モデル分担の検討メモ

作成日: 2026-09-05

状態: **未採用・未検証の提案**。ユーザーは議論を記録することを了承した。以下を運用ルールとして採用したり、モデル別の優劣を確定したりしたものではない。エージェント間の通知・自動割り当ては未実装。

## 目的と背景

Codex と Claude Code、Astra と Fable などのモデルが協力し、作業の競合と待ち時間を減らす。ユーザーが毎回、担当間の情報を運ぶ負担も減らしたい。

今回、Claude が phase6-3 を進めている間に Codex で issue #90 を扱えるか調査した。確認時の checkout は `main`、commit `0ca61c212b96f77ac5775ce20bb33cc9cc4efb1a`。ローカルの未追跡計画 `docs/superpowers/plans/2026-09-05-broker-kernel-6-3-egress.md` と issue 本文・現行コードを照合すると、両方が `src/agent_container/broker/runtime.py` の `SocketBrokerRuntime.stop()` を変更する内容だった。このため #90 の実装は進めず、phase6-3 のマージ後に別 PR で扱う順序を提案した。これは調査時点の判断であり、着手時には最新状態を再確認する。

競合がある場合にも、不具合の再現確認や検証観点の整理など、独立して進められる仕事を探す余地があった。ただし、この会話では #90 の再現実験や修正・テスト追加は行っていない。

## 分担の初期案

文脈を持っている側を主担当にし、もう一方が独立した検証を担当する。モデル名による固定分担は、実績を見て調整する。

| 作業 | 担当の初期案 | 理由 |
| --- | --- | --- |
| phase 全体の設計・継続実装 | その phase を進めている側。今回なら Claude | 設計経緯を引き継ぐ負担を抑える |
| 停止処理・並行処理・権限境界の検証 | 主担当とは別の Astra / Fable | 前提と失敗条件を独立して点検する |
| 独立した issue の実装 | 空いている側 | 変更範囲と完了条件を明確にして並行化する |
| 難しい不具合の原因究明 | Astra / Fable の一方。行き詰まったら他方 | 別の仮説を得る |
| ログ整理・関連箇所の探索・定型的な文書更新 | 速度・費用を優先したモデルを試す | 狭い仕事から適性を確認する |
| 統合・最終確認 | あらかじめ決めた一人 | マージ順序と検証結果の管理を一本化する |

Codex / Claude Code という実行環境の違いと、Astra / Fable というモデルの違いは分けて評価する。利用できるツール・権限・指示・既存の文脈によって結果が変わるため、差をすべてモデルの能力に帰属させない。

## 連携で試したいこと

- 担当、変更予定ファイル、依存する作業、完了条件を共有する。具体的な共有方式は未設計。
- 実装と検証を分担する。検証側には要求・対象 commit・守るべき動作を渡し、実装者の説明だけに依存せずテスト観点を考えてもらう。
- 指摘の採否は再現やコード上の根拠で判断する。異なるモデルの一致だけを正しさの保証にしない。
- 同じ処理を変更する場合、別 worktree でも統合時の調整は必要と考える。待ち時間には再現確認、仕様調査、検証準備などを候補にする。
- 数件ごとに所要時間、手戻り、人の介入回数、有効な不具合の発見を振り返り、このリポジトリでの適性を見直す。

今回の候補は、Claude が phase6-3 を実装する間に、Codex が #90 の listener close 失敗後の再試行、worker が残る場合、session の後片付けも失敗する場合の検証観点を整理すること。これは今後の候補であり、実行済みではない。

## 一次情報と解釈の限界

2026-09-05 に以下の公式資料を確認した。

- [OpenAI: Model guidance — GPT-6 Astra](https://developers.openai.com/api/docs/guides/latest-model): 複数ツールにまたがる多段階の作業、ソフトウェア開発、検証を特徴として説明している。
- [Anthropic: Claude Fable](https://www.anthropic.com/claude/fable): 確認時には Fable 5.1 の大規模なコード変更、レビュー、長時間の自律作業を説明している。
- [Issue #90](https://github.com/jj1xgo/agent-container/issues/90): listener close 失敗後の再試行が抑止される不具合と、振る舞い保存のリファクタリングから修正を分離する背景。

公式のモデル紹介は、同条件で両者を比較したこのプロジェクトの評価結果ではない。「設計は Claude、実装は Codex」などの固定的な優劣は、確認した資料からは確定できない。上記の分担表は運用上の仮説である。モデル名・版・提供状況は変わるので、実際の採用時に再確認する。

## 記録の使い分けと次の検討

本メモを議論の参照先にし、handover には参照先とその時点の進捗を記録する。試して有効だと確認できたルールは、改めて採用を決めてから AGENTS.md などの継続的な指示へ反映する。
