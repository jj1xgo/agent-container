# v0.4.1 Version and Release Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Publish a narrowly scoped `v0.4.1` maintenance release that fixes exact-tag version reporting, then merge a reviewed main forward-port that reports the `0.5.0-dev` line and advertises `v0.4.1` as stable.

**Architecture:** A focused Python metadata module supplies release, development-base, development-series, and fallback values to the existing resolver. A `release/0.4` branch based on immutable `v0.4.0` produces the patch, while a separate main PR adapts the same contracts without importing post-`v0.4.0` features into the patch.

**Tech Stack:** Python 3.11 standard library, `unittest`, Git, GitHub Actions, rootless Podman, GitHub CLI.

**Spec:** `docs/superpowers/specs/2026-09-01-v0.4.1-version-release-design.md`

## Global Constraints

- Never move, overwrite, delete, or reuse published tag `v0.4.0` or `v0.4.1`.
- Build `release/0.4` from exact tag `v0.4.0`; do not merge current main feature work into it.
- Keep existing untracked `bin/rg`, unrelated worktrees, and unrelated branches untouched.
- On the maintenance release tag, `bin/agentctl --version` must be exactly `agentctl 0.4.1`.
- On post-release main, the checkout version must be `0.5.0-dev.N+gCOMMIT`, with `.dirty` only for tracked changes.
- The main README must distinguish `Latest stable: v0.4.1` from `Development branch: main (0.5.0-dev)`.
- Prepare and review the main forward-port before publication, but merge it only after the GitHub Release exists.
- Stop for explicit user approval after presenting the exact candidate commit, all verification evidence, and final release notes; do not create or push the real tag before that approval.
- Do not record an unavailable or skipped verification gate as passing.
