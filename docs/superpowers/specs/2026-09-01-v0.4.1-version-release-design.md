# v0.4.1 version and release design

## Purpose

Correct the released `v0.4.0` version resolver without moving or replacing the
published tag, publish the correction as the narrowly scoped `v0.4.1` patch
release, and prevent release metadata, CLI output, and repository guidance from
drifting apart again.

The current `main` branch contains substantial post-`v0.4.0` feature work. It
must not be labeled as a patch release. The patch is therefore produced from a
maintenance branch based on `v0.4.0`, then the reusable correction and release
contracts are adapted and forwarded to `main`.

## Release topology

Create `release/0.4` from the immutable `v0.4.0` tag. The maintenance change is
limited to version resolution, its tests, release documentation, and the
minimum CI contract needed to verify the release. After review and required CI,
merge the maintenance pull request and use that exact merge commit as the
`v0.4.1` release candidate.

Keep `release/0.4` after publication as the maintenance line for any future
critical `0.4.x` correction. Do not merge post-`v0.4.0` features into it.

Before publication, prepare and review a separate main forward-port of the same
metadata model, resolver correction, documentation contract, and CI visibility,
but do not merge it while `v0.4.1` is still unpublished. After `v0.4.1` is
published, merge the already reviewed forward-port. The main branch continues as
the `0.5.0-dev` development line while its README identifies `v0.4.1` as the
latest stable release.

## Version metadata

A small Python metadata module is the single machine-readable source for:

- the release tag and corresponding release version;
- the development base tag used for commit-distance calculation;
- the development version series; and
- the no-Git fallback version.

These values are separate because the latest stable maintenance tag need not be
an ancestor of `main`. On `release/0.4`, the release is `v0.4.1` and development
work leading to it remains in the `0.4.1-dev` series based on `v0.4.0`. On
`main`, the public stable release is `v0.4.1`, while development remains in the
`0.5.0-dev` series with an explicit ancestor tag as its distance base.

README and CHANGELOG remain human-readable tracked files. Contract tests compare
their release declarations with the metadata instead of generating them, so the
GitHub repository page stays readable and an omitted manual update fails CI.

## Resolver behavior

For a usable Git checkout, the resolver obtains the seven-character commit ID
and checks tracked-file status. Untracked files do not make the version dirty.

A clean checkout exactly at the configured release tag resolves to the release
version. Otherwise, the resolver verifies that the configured development base
is an ancestor and counts first-parent commits from that base. The result is:

`DEVELOPMENT_SERIES.N+gCOMMIT`

Tracked changes append `.dirty`. First-parent counting prevents commits inside a
merged topic branch from inflating the development sequence.

If the development base is absent, shallow, or not an ancestor, the resolver
retains the commit identity and uses distance zero. It must not accidentally use
an unrelated maintenance tag as the main development base.

When Git metadata is unavailable, a valid SemVer value embedded through the
existing `AGENT_CONTAINER_VERSION` interface takes precedence. Invalid embedded
values are rejected, after which the configured fallback is returned.

## Public documentation

The README introduction distinguishes the two supported choices:

- `Latest stable: v0.4.1`, installed by cloning or checking out that tag; and
- `Development branch: main (0.5.0-dev)`, obtained by a normal default clone.

The README does not contain a manually maintained commit distance because it
changes on every first-parent commit. Users obtain the exact checkout version
with `bin/agentctl --version`.

The `v0.4.1` CHANGELOG and release notes state that `v0.4.0` does not recognize
its own exact tag because its resolver remained based on `v0.3.0`. They explain
that published `v0.4.0` is immutable and that `v0.4.1` is the corrected patch.

## CI and release contracts

Automated tests cover:

- lightweight and annotated exact release tags;
- development output after the release base;
- first-parent distance across a merge;
- tracked dirty state and ignored untracked state;
- a checkout without the configured tag;
- valid embedded versions, invalid SemVer, and fallback behavior;
- agreement among metadata, README, and CHANGELOG;
- the maintenance `0.4.1` contract; and
- the main `0.5.0-dev` contract.

CI writes the resolved agent-container version to the GitHub Actions job summary
to reduce diagnosis time. This is supplementary evidence, not a replacement for
tests or README disclosure.

Before publication, verify the candidate in a temporary clone. Add a local-only
candidate `v0.4.1` tag there and confirm exact CLI output without changing the
real repository. Run the full unit suite, documentation contracts, lint,
`git diff --check`, the maintenance branch's configured Podman integration,
candidate image version checks, and all required GitHub PR checks. Any
unavailable gate is reported explicitly and is not recorded as passing.

## Publication and failure handling

After the maintenance candidate and forward-port are reviewed, present the exact
candidate commit, changes, test and CI evidence, and proposed release notes to
the user. Stop for explicit final approval before creating or publishing the
real tag or GitHub Release.

After approval:

1. create annotated tag `v0.4.1` on the approved commit;
2. push only that tag;
3. verify the remote tag resolves to the approved commit;
4. create the GitHub Release from that tag; and
5. read back the release and its notes.

If tag push succeeds but GitHub Release creation fails, do not delete, move, or
replace the tag. Diagnose the failure and retry release creation from the same
tag. If a published tag points to an unexpected commit, stop and report it;
never force-update a published tag.

## Completion criteria

The work is complete only when `v0.4.1` is published from the reviewed
maintenance commit, the GitHub Release is verified, and `main` visibly identifies
`v0.4.1` as stable while resolving itself as `0.5.0-dev.N+gCOMMIT`. Existing
untracked `bin/rg`, unrelated worktrees, and unrelated branches remain untouched.
